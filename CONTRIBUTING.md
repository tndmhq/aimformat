# Contributing

Thanks for your interest in `.aim`. The repo carries the v0.6 draft of the
spec and the reference toolkit; breaking changes are possible until 1.0,
and design discussion via issues is as welcome as PRs.

Whether you are a human, an AI agent, or a human driving an AI agent, the
path to a good PR is the same:

1. Read [`AGENTS.md`](AGENTS.md): repo purpose, layout, and the working
   conventions (package pinning, planning, memory rules, git etiquette). If
   you use Claude Code, Cursor, or any agent that honors `AGENTS.md` /
   `CLAUDE.md`, it will pick these up automatically.
2. Skim [`docs/knowledge/`](docs/knowledge/) (and
   [`docs/log/index.md`](docs/log/index.md) for recent context) so your change
   fits decisions already made.
3. Open a PR that conforms to the conventions: focused commits, clear
   messages, pinned dependency versions.

## Development setup

```sh
git clone https://github.com/tndmhq/aimformat && cd aimformat
pip install -e '.[dev]'        # pytest + the interop test deps, all pinned
git config core.hooksPath .githooks   # the pre-commit hook, once per clone
python3 -m pytest              # the whole suite, a few minutes
```

The pre-commit hook runs what CI's lint job runs on the files you commit:
`ruff check`, `ruff format --check`, and `mypy src` when `src/` changes
(`prettier` and `tsc` for `ts/`). Please don't bypass it with `--no-verify`;
if it can't find `ruff` and `mypy`, it tells you where it looked.

The package is stdlib-only at runtime; please keep it that way. Heavy or
optional integrations go behind extras (`[docx]` is the pattern) with lazy
imports and a clear install hint in the raised error.

## How the moving parts fit together

One registry drives everything; most changes touch it plus one artifact:

- `src/aimformat/registry.json` is the vocabulary (elements, classes,
  style whitelist, theme slots, event schemas, rule codes). Change it and:
  - regenerate the spec appendix: `python3 scripts/gen_spec_appendix.py`
    (CI fails on a stale appendix);
  - regenerate the TypeScript tables:
    `python3 scripts/gen_ts_registry.py` (`tests/test_ts_registry.py` fails
    on a stale `ts/src/registry.data.ts`);
  - the linter, `aim.css` and the paint resolver pick it up automatically
    (all three read the registry at import time).
- `spec.md` is the normative text. Every ` ```aim ` fenced block is a
  complete document that CI lints (`tests/test_spec.py`); anything that is
  not one — an intentionally invalid example, or a fragment showing a single
  element — must use plain ` ```html ` fences, and pin its conformance claim
  in the test suite instead. Keep snippets canonical. The C001 finding
  prints the exact expected line when you get it wrong.
- `tests/fixtures/` is the conformance suite: `ok_*.aim` must lint clean,
  `nok_<CODE>_*.aim` must trigger exactly `<CODE>`. One rule per file.
  Regenerate with `python3 scripts/gen_fixtures.py` (which also
  sanity-checks the expectations).
- `examples/` is generated by `python3 scripts/gen_examples.py`; never
  hand-edit the `.aim` files.

## Tests

Every behavior change comes with tests. The suite is organized by concern
(`test_canonical`, `test_document_ops`, `test_proposals`, `test_history`,
`test_lint`, `test_ingest_export`, …); a new lint rule needs its rule code
in the registry, a `nok_` fixture, and a targeted test. Run
`python3 -m pytest` before pushing. CI runs the same thing across Python
3.10–3.13.

### The LibreOffice check of the tracked-change shapes

The tracked-change shapes in `tests/tracked_docx_kit.py` each declare what
Word leaves after Reject All and Accept All. CI's `tracked-oracle` job checks
those declarations against LibreOffice on every push: it writes the shapes
with `scripts/gen_docx_tracked.py` and resolves them with
`scripts/libreoffice_oracle.py` (details in
`tests/fixtures/docx-tracked/README.md`). The job is not a merge gate yet.

To run it locally:

- **On Linux**, as CI does: install `libreoffice-writer` and `python3-uno`,
  then run `python3 scripts/gen_docx_tracked.py OUT` and
  `/usr/bin/python3 scripts/libreoffice_oracle.py OUT`. The oracle needs the
  system Python that has LibreOffice's `uno` module.
- **Anywhere Docker runs**, including macOS: build the image once with
  `docker build -t aim-oracle:24.2.7 scripts/oracle-docker`, then run
  `scripts/run_oracle_docker.sh . OUT`. It writes the shapes on the host and
  resolves them in the container, with LibreOffice 24.2.7, as CI had it.
  On macOS, don't run the oracle with the Python that ships inside
  LibreOffice.app: macOS stops it when a shell starts it.

## Releasing (maintainers)

The package is live on PyPI: <https://pypi.org/project/aimformat/>. Releases
are wired for [PyPI Trusted
Publishing](https://docs.pypi.org/trusted-publishers/), so there are no API
tokens anywhere. The one-time setup has been in place since 2026-07-10:
the PyPI project trusts owner `tndmhq`, repository `aimformat`, workflow
`publish.yml`, environment `pypi` (re-add under the project's
Settings → Publishing if it's ever lost). Per release:

1. Bump `__version__` in `src/aimformat/__init__.py` (the single source;
   pyproject reads it) and give the unreleased block in `CHANGELOG.md` its
   version heading and date. A version that never shipped keeps its own
   heading, retitled `## X.Y.Z — unreleased (folded into <released>)`, so
   the file still records which construct arrived in which spec minor.
   Check the version claims that ship *with* the release while you are
   here: `README.md` is the PyPI project page, and its "the spec is a vN
   draft" line and Status-and-roadmap list are the two that go stale.
2. `python3 -m pytest` green; `git tag v<version> && git push --tags`.
3. Create a GitHub release for the tag; publishing it triggers
   [`publish.yml`](.github/workflows/publish.yml), which builds sdist +
   wheel and uploads to PyPI via OIDC.

## Notes specific to external PRs

- You are not required to append to `docs/log/`; the episodic log is a
  maintainer tool, kept light.
- Changes to `docs/knowledge/` are maintainer-authoritative: you may
  propose edits, but expect stricter review there than on code.
