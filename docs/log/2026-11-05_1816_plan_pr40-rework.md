# Rework #40: compact TOC, images stored once, oracle nesting, records

## Why

The maintainer went through the format decisions on 2026-11-05. Two of them change
this PR: the table of contents (TOC) gets a compact shape with a read-by-section call,
and imported images are stored once (IMPORT-D15 is no longer deferred). The maintainer
is away while this rework runs: every choice he has not made is implemented here
provisionally, numbered P1-P18 below, and listed in the PR for his review. Nothing is
merged. `origin/main` (0.5.3, `to_print_html`, the pre-commit hook) was merged in
(4eb432e). The failing `tracked-oracle` check is fixed too.

## Decided by the maintainer (2026-11-05)

1. **Compact TOC.** One entry per section with its title, level, the heading's id, a word
   count and a chunk count; no list of every block id. A call reads one section by its
   heading's id and returns the section's ids, its text or its exact markup. The MCP side
   of that call belongs to the agent-reads rework (#42).
2. **Images stored once.** The baseline keeps its full copy of the text; imported images
   are moved into the asset registry before the baseline is recorded, so the body and the
   snapshot point at one stored image.
3. (His leaning, to confirm:) one 0.6 release instead of IMPORT-D14's two.

## Provisional choices, awaiting the maintainer

TOC:

- **P1. Field names** `id`, `level`, `title`, `word_count`, `chunk_count`. Stored JSON
  sorts its keys (canonical JSON, §11.2), so a stored entry reads `chunk_count`, `id`,
  `level`, `title`, `word_count`; the Python `Section` may present them in any order.
  Alternative: `words`/`chunks`, about 6% fewer tokens, but `chunks` was the old list key.
- **P2. Section extent.** A section opens at a top-level addressable `h1`-`h6` (level = its
  rank) or an `aim-slide` (level 1, id = the slide's container id, title = its first
  heading) and runs to the next opener of the same or a higher level, so it includes its
  subsections and its counts include theirs. Slides follow the same rule. Content before
  the first opener is an untitled level-1 entry whose id is the first top-level
  construct's id.
- **P3. Counts.** `chunk_count` = distinct chunk ids in the section (list items and table
  rows count one each, a run counts once, containers count zero). `word_count` =
  whitespace-separated tokens of the visible text; block, item, row and cell boundaries
  and `<br>` separate words; `img`, `svg`, `template`, `script` and `style` contribute
  nothing. The counts are informative: lint checks the entry shape and the freshness
  hash, never recomputes counts.
- **P4. Every save builds the TOC** when the document has a heading or a slide (today a
  save only refreshes an existing one), **in documents declared 0.6 or later only**. A
  document declared below 0.6 keeps its meta block exactly as it is, so 0.5 tools never
  see a TOC-only meta block (their M004 requires a summary). In a 0.6+ document an
  old-shape entry counts as stale (M005) and is rewritten on save; below 0.6 the old shape
  is that version's valid shape and gets no finding.
- **P5. Keep the rest of IMPORT-D13:** `toc_doc_hash`, refresh on save, M005, `summary`
  optional, `aim_read`'s `toc_source`.
- **P6.** A document with no heading or slide stores no TOC (as today).
- **P7. Python API:** `AimDocument.section(section_id) -> Section`, a frozen dataclass with
  `id`, `level`, `title`, `word_count`, `chunk_count`, `ids` (chunk and container ids, a
  container before its items), `text` (one line per chunk), `html` (the section's
  top-level construct lines, exactly as in the file) and `entry()` (the stored dict). An
  id that opens no section raises `TargetNotFound`. Pending proposals are not included.
  The counting lives in a new module `toc.py`, so #42's views can import it.
- **P8.** Numbered clauses (`num-1`/`num-2` blocks) do not open sections here; #42
  decides that for its agent outline.

Images:

- **P9. Pack both tracked views.** A tracked DOCX import packs the reject view and the
  accept view through one content-addressed collection before alignment, and registers
  images that only the accept view has before the lane is written. Packing only the body
  made every tracked import with an image raise `ParseError` (the lane validator compares
  the packed body with the unpacked accept view).
- **P10. Formats packed:** PNG, JPEG and GIF, whose dimensions the SDK reads. BMP, WebP and
  TIFF stay inline (the SDK cannot size them, and TIFF does not render in Chromium in
  either form). Alternative: add BMP and WebP readers.
- **P11.** A data URI that does not decode as strict base64 stays inline and the import
  goes on (the DOCX importer adds a report warning), instead of aborting an import that
  works today.
- **P12.** Asset garbage collection counts references in baseline snapshots (a bug: today
  an out-of-band delete followed by any gc leaves the snapshot pointing at nothing).
- **P13. Two new lint warnings** for packed images, whose bytes sit outside `doc_hash`: a
  `use href="#asset-…"` that resolves to no symbol (body, pending payloads, retained
  history including snapshots), and an asset id that does not match the sha256 of its
  bytes (§9.2). Warnings, not errors, until the maintainer decides.
- **P14. Spec §7 wording:** the asset registry is content-addressed state, excluded from
  `doc_hash` but not regenerable, since after an import it holds the only copy of each
  image.
- **P15.** `to_docx` and `to_markdown` export packed images (a bug: today both drop them
  silently, so a DOCX round trip of an imported file would lose every image).

Oracle:

- **P16.** The tracked-change kit writes Word's nesting (insertion outside deletion) for
  `nested_del_ins`. A new shape `nested_del_outside_ins` keeps the other nesting; the
  oracle still runs it and reports it as a known LibreOffice misreading (LibreOffice drops
  the deletion when `w:del` wraps `w:ins`), and says so when LibreOffice starts agreeing.
  Our importer is right on both shapes. `tracked-oracle` stays non-gating; no LibreOffice
  bug is filed from here.

Records and process:

- **P17.** New decision entries supersede IMPORT-D13 (`toc-compact-sections`, D13b,
  active), IMPORT-D15 (`import-packs-images-before-baseline`, D15b, active) and IMPORT-D14
  (`single-0-6-release`, D14b, todo: the maintainer's leaning). The old entries and the
  2026-10-01 report flip to superseded; a new report closes this plan.
- **P18.** `origin/main` merged rather than rebased (#42, #41 and #39 are stacked on this
  branch; no force push). Conflicts: `__version__` stays 0.6.0; the CHANGELOG's planned
  "0.5.3" tracked-change notes move into 0.6.0 (0.5.3 shipped on 2026-10-14 without them)
  and main's real 0.5.3 entry follows.

## Out of scope

- A downstream editor's support for packed images: the one this format was built with does not show them today. That work is
  a hard prerequisite for the editor's move to a 0.6 that packs, not part of this PR.
- The MCP section read, numbered clauses in the outline, and aligning #42's outline
  (`views.py`) with this shape: the #42 rework.
- CJK word counting; asking docling for picture images in the SDK's `from_pdf`; images
  added after import (they stay inline in history events); the exporter's own
  deletion-outside-insertion nesting around page breaks (LibreOffice reads it correctly);
  pinning the CI runner or making `tracked-oracle` gating.
- The old TOC shape shown in other repositories' snippets: follow-ups at release.

## Risks

- Version skew: a 0.5.3 tool reports M004 (error) on a TOC-only meta block. P4's gate keeps
  0.5-declared documents unchanged; 0.6 documents already need a 0.6 tool.
- `dumps()` now adds a head block to an in-memory 0.6 document with a heading (exports
  call `dumps()`).
- Conflicts when #42 is rebased (`mcp.py`, `docs/for-agents.md`, its goldens).
- Packed bytes leave `doc_hash`: P13 restores detection as warnings.

## Changes during the work (2026-11-05)

Each package was built in its own worktree and reviewed adversarially by a second agent
that fixed what it found (a quadratic section scan, missing tests, docs that disagreed with
the code, an oracle note that never printed). Integrated, the branch then went through a
three-lens review (integration, consistency, compatibility) before any push. What changed
against the items above:

- **New lint codes renumbered:** the asset warnings are S036 and S037, leaving S035 to the
  stacked auto-accept branch (#39), which already uses it.
- **P4 tightened:** `generate_toc()` raises `InvalidOperation` in a document declared below
  0.6 (it wrote a TOC-only block that 0.5 tools reject and that saves then left stale).
  Lint judges the declared version: below 0.6, M004 still requires a summary and there is
  no entry-shape check.
- **P6 corrected:** a save removes a stored TOC (and an emptied meta block) once the body
  has no heading or slide; the package had kept one untitled entry.
- **P1 detail:** only a `chunks` *list* marks the pre-0.6 shape; another `chunks` value is an
  ignored unknown field.
- **Fixed in the tracked import (older than this rework):** a tracked insertion, deletion
  or replacement of a paragraph holding only a picture produced no card, so accept-all
  differed from Word's; revisions are now also looked up by the base key of a derived
  figure key.
- **Conformance kit:** the generator's `#asset-unused` reference made S036 fire in two old
  fixtures; it now uses a non-asset fragment.
- **Compatibility, for the maintainer:** a 0.6 document saved with a heading or a slide and
  no summary carries a TOC-only meta block, which a 0.5 tool reports as M004. A downstream
  tool that lints such files needs 0.6 before those files reach it: the release order (a
  0.5.4 that skips rules of newer declared versions, holding 0.6 on PyPI until the editor
  pins it, or saves that only refresh an existing TOC until then) is his call.
- **Follow-ups outside this PR:** an editor that renders `<aim-assets>` and counts only live
  assets against its size ceiling; #42's rework (its outline and text view on this shape,
  the MCP section read, the conflicts and goldens the rebase brings).
